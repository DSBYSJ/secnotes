# 报告撰写与风险评级

## 报告写给两类人

| 读者 | 关心 | 看哪部分 |
|---|---|---|
| 管理层 / 业务方 | 会不会出事、要花多少钱、什么时候能修 | 执行摘要、风险总览 |
| 技术团队 | 在哪、怎么复现、怎么修 | 漏洞详情、修复建议 |

一份报告如果只有技术细节，客户老板不会批预算；如果只有摘要，工程师修不了。**两部分都要有，且不能混**。

## 标准结构

```
1. 封面与版本
2. 执行摘要（1 页，无技术术语）
3. 测试范围与方法
4. 风险总览（统计表 + 趋势）
5. 漏洞详情（每条独立成节）
6. 修复建议汇总（按优先级）
7. 附录：工具、时间线、测试账号、术语表
```

## 执行摘要怎么写

三句话结构：

1. **测了什么**：范围、时间、方式
2. **发现了什么**：按等级统计 + 最严重的 2-3 个问题的**业务影响**
3. **建议做什么**：按优先级给 3 条动作

反例（技术语言）："存在 SQL 注入，可通过 union 注入获取数据库数据。"

正例（业务语言）："登录接口存在注入缺陷，攻击者无需账号即可读取用户表，涉及约 12 万条手机号与密码哈希。建议 72 小时内修复并评估数据泄露通报义务。"

## 单条漏洞的六要素

| 要素 | 要求 |
|---|---|
| 标题 | 位置 + 类型，例如"订单查询接口存在 SQL 注入" |
| 风险等级 | 附评级依据 |
| 影响 | 具体到"能干什么"，不写"可能导致严重后果" |
| 复现步骤 | 编号步骤 + 原始请求 + 响应证据 |
| 修复建议 | 可执行，到代码/配置层面 |
| 参考 | CWE / OWASP 分类 |

### 复现步骤的粒度

```
1. 登录测试账号 test01
2. 访问 /api/order?orderId=1001
3. 将 orderId 改为 1001 and 1=1，返回正常
4. 改为 1001 and 1=2，返回空列表
→ 判定为布尔盲注
```

要能让**没参与测试的工程师**照着做一遍就复现。

## 风险评级

### CVSS 只是起点

CVSS 3.1 的基础分看四个维度：

```
Attack Vector (网络/邻接/本地/物理)
Attack Complexity (高/低)
Privileges Required (无/低/高)
User Interaction (无/需要)
→ 机密性 / 完整性 / 可用性影响
```

但真实项目里，**业务影响往往比分数更重要**：

| 情况 | 处理 |
|---|---|
| 内网 SSRF，但能打到云元数据 | 上调（凭据泄露） |
| 存储型 XSS，但只影响自己 | 下调（无横向） |
| SQL 注入，但库是只读测试库 | 下调（影响有限） |
| 弱口令，但账号是离职员工 | 下调，但要提"账号未清理" |

### 常用分级

| 等级 | 含义 | 修复时限建议 |
|---|---|---|
| 严重 | 可直接获取核心权限/数据 | 24-72 小时 |
| 高危 | 可获取部分权限或敏感数据 | 1-2 周 |
| 中危 | 需要组合条件，影响有限 | 1 个月 |
| 低危 | 信息泄露、加固类 | 下个迭代 |

> [!TIP]
> 报告里写清"评级理由"，比分数本身重要。客户的安全团队要拿它去说服业务方，理由必须站得住。

## 常见错误

- **夸大**：把信息泄露写成"可导致服务器沦陷"
- **含糊**：修复建议写"加强安全意识"
- **无证据**：截图没有 URL、没有时间、没有请求原文
- **越界内容**：把范围外资产的问题写进正式报告
- **不复测**：修完不验证，客户以为修好了

## 修复建议的写法

差："对输入进行过滤。"

好：

```
1. 使用参数化查询（PDO prepare / MyBatis #{}）
2. 数据库账号降权：移除 FILE、PROCESS 权限，仅授予业务表 DML
3. 关闭详细错误回显，统一错误页
4. 上线前用 sqlmap 对同一接口回归（--batch --level 2）
```

**给到能直接派工单的程度**，客户才会真的修。

## 复测

复测只做两件事：

1. 原漏洞是否已修复
2. 修复是否引入新问题（例如加了 WAF 但绕过依然有效）

复测结论单独出一页，不要混在初测报告里。
