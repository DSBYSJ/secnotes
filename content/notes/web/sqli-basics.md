# SQL 注入：从探测到验证

> [!NOTE]
> 本笔记只讨论**在授权目标上**的检测与验证方法，不提供脱库、提权等后续利用步骤。验证到"能证明存在"就应停止。

## 本质

用户输入被当成 SQL 语法的一部分执行，而不是数据。

```php
// 错误：拼接
$sql = "SELECT * FROM users WHERE id = " . $_GET['id'];

// 正确：预编译
$stmt = $pdo->prepare("SELECT * FROM users WHERE id = ?");
$stmt->execute([$_GET['id']]);
```

所有注入类型、所有绕过技巧，根子都在第一行代码。

## 第一步：找注入点

注入点不只在 `?id=1`，常见的还有：

| 位置 | 例子 | 备注 |
|---|---|---|
| GET 参数 | `?id=1` | 最直观 |
| POST 表单 | 登录框、搜索框 | 注意 JSON 体 |
| Cookie | `uid=123` | 常被遗忘 |
| HTTP 头 | `X-Forwarded-For`、`Referer` | 写日志的接口容易中 |
| 排序/分页 | `order=id desc`、`limit=0,10` | 拼接重灾区 |
| 二次注入 | 注册时写入，查询时触发 | 需要两步 |

### 探测手法

原则：**制造语法错误，观察行为差异**。

1. 加一个单引号 `'`，看是否 500 / 报错 / 页面结构变化
2. 数字型：`and 1=1` 与 `and 1=2` 的结果是否不同
3. 字符型：`' and '1'='1` 与 `' and '1'='2`
4. 括号闭合：`') and ('1'='1`
5. 编码绕过：`%27`、`%bf%27`（宽字节）

> [!TIP]
> 判断"是否有差异"时，不要用肉眼。用响应长度、状态码、关键词出现次数做对比，或者直接上 `ffuf` 跑一组变异。

## 六种类型

| 类型 | 特征 | 判断方式 |
|---|---|---|
| 联合注入 | 有回显 | `order by` 猜列数 → `union select` |
| 报错注入 | 报错信息回显 | 构造类型转换/重复键错误 |
| 布尔盲注 | 无回显，但页面有真假差异 | `and 1=1` vs `and 1=2` |
| 时间盲注 | 无回显无差异 | `and sleep(5)` 观察响应时间 |
| 堆叠注入 | 支持多语句 | `; select ...`（MySQL+PHP 少见） |
| 二次注入 | 存入时转义、取出时拼接 | 需要业务链路配合 |

### 联合注入的关键两步

```
1. 猜列数：order by 1 / 2 / 3 ... 直到报错
2. 找显示位：union select 1,2,3 -- 看哪一列被渲染
```

### 时间盲注的坑

网络抖动会让 `sleep(5)` 误判。做法：**多次采样取中位数**，并设置一个足够大的阈值（例如 4 秒）。

## 用 sqlmap 的正确姿势

sqlmap 很强，但**默认参数会打得很凶**，还可能把库拖下来。约定：

```bash
# 先只做检测，不取数据
sqlmap -r req.txt --batch --level 2 --risk 2 --dbms=mysql --technique=BEU

# 指定参数，避免全参数扫描
sqlmap -u "https://target/item?id=1" -p id --batch

# 只确认可注入，不做后续
sqlmap -r req.txt --batch --flush-session --parse-errors
```

参数说明：

| 参数 | 作用 | 注意 |
|---|---|---|
| `-r` | 从 Burp 保存的请求文件读 | 保留 Cookie/UA，最贴近真实 |
| `--level` | 检测深度 1-5 | 3 以上会测更多 header |
| `--risk` | 风险 1-3 | 3 会尝试 UPDATE，**别在生产用** |
| `--technique` | 指定技术 | B 布尔 E 报错 U 联合 T 时间 S 堆叠 |
| `--tamper` | 变形脚本 | 针对 WAF，如 `space2comment` |
| `--flush-session` | 清缓存重测 | 换了参数必须加 |

> [!WARNING]
> `--risk=3` 可能修改数据，`--dump` 会拉取业务数据。这两件事在真实项目中都需要**书面许可**。

## WAF 绕过的思路

不是背 payload，而是理解 WAF 看什么：

1. **关键字**：`union select` → 注释拆分 `un/**/ion sel/**/ect`
2. **空格**：`%09`、`%0a`、`+`、括号
3. **大小写与编码**：`SeLeCt`、`%53elect`、双重 URL 编码
4. **语义等价**：`and 1=1` → `and true`、`&&`
5. **参数污染**：`?id=1&id=2` 后端取值不一致

这些手段本质是**探测 WAF 规则的边界**，属于授权测试范围内的常规操作。真正该报告的是"WAF 后面那个没修的漏洞"。

## 验证到什么程度算够

| 目的 | 证据 |
|---|---|
| 证明存在 | 布尔差异截图 / 报错信息 / 时间延迟记录 |
| 证明影响 | 能读到当前库名、当前用户（`database()`、`user()`） |
| 不建议 | 全表 dump、写文件、提权 |

报告里写"可读取数据库名与当前用户，说明越权读取业务数据可行"，比贴一万行数据更有说服力，也更安全。

## 修复

1. **预编译参数化**（唯一根治手段）
2. 输入校验（类型、长度、白名单）—— 辅助，不是替代
3. 最小权限数据库账号（禁止 `FILE`、禁止跨库）
4. 关闭详细报错，统一错误页
5. WAF —— 争取时间，不解决问题
